# Security and Compliance Review: Konoha Project v2.0.0-beta.8

## Executive Summary

This review covers the Konoha MCP runtime v2.0.0-beta.8, certifying two workstreams completed on **2026-09-09**: (1) the new **Command Code native-tool blocker** — a `PreToolUse` hook enforcement layer that closes the native-file-read bypass in Command Code (`permissions.allow: ["*"]` cannot deny native tool calls), and (2) **RTK rule deployment hardening** across the Command Code, Claude Code, and Codex clients — eliminating the `rtk-rule-template-missing` failure mode, fixing a template-literal escaping bug that produced an invalid generated blocker script, and removing an invalid `rtk init --codex` invocation (no `codex` agent exists in RTK 0.44.1).

The release maintains the beta.7 baseline: 39 MCP tools, 16 CLI commands, 7 ninja subagents, and 7 client integrations (Antigravity IDE/CLI, Cursor, Claude Code, OpenCode, Command Code, Codex, and Pi/pi.dev) on the pure Node.js single-runtime architecture. All fixes were verified by direct regeneration and behavioral testing (not source inspection alone): generated scripts pass `node --check`, deny/allow decisions were exercised via stdin simulation, and all manager file copies were byte-verified in sync across the three runtime locations.

## Findings & Compliance Verification

### 1. Command Code Native-Tool Blocker Enforcement (new in beta.8)
- **Threat Model**: Command Code ships 4 native tools (`shell_command`, `read_file`, `write_file`, `edit_file`) and its `permissions.allow: ["*"]` model cannot express a deny for native reads — agents could bypass the mandatory konoha/semble MCP tool contract using native `read_file`.
- **Control**: A Node.js payload at `~/.local/bin/konoha-native-blocker-cc.js` is registered as a `PreToolUse` hook in `~/.commandcode/settings.json`, mirroring the Claude Code native blocker. The hook matcher is deliberately omitted so the hook fires on every tool invocation; the script filters on `tool_name === "read_file"` and exits 0 silently for all other tools (no STDOUT pollution, no interference with non-target tools).
- **Protocol Conformance**: Deny responses use only the documented `hookSpecificOutput.permissionDecision: "deny"` shape, redirecting the agent to the konoha MCP bounded file tools (`read_file_head`, `read_file_range`, `file_info`, `get_file_structure`, `find_files_clean`, `token_efficient_grep`) or the semble MCP for codebase search.
- **Verification**: Behavioral stdin testing confirmed: `read_file` → deny JSON with exit 0; `write_file` (non-target) → silent exit 0; non-JSON input → graceful exit 0. `ensureCommandCodeSetup` returns `{"ok":true,"rtk":"already-installed","rtkRule":"deployed","contractRule":"deployed","nativeBlocker":"deployed"}`.
- **Compliance Status**: **PASS** (Native-read bypass closed; deny path verified behaviorally).

### 2. Generated Script Payload Integrity (fixed in beta.8)
- **Finding**: The generated `konoha-native-blocker-cc.js` contained a literal newline inside a string literal (a SyntaxError at load time) because the payload template literal in `src/mcp_clients_manager.js` emitted a real newline instead of the required literal two-character backslash-n sequence.
- **Fix**: The template now double-escapes (`'\\n'` in source) so the generated script contains the literal `\n` escape sequence. The full payload template was audited for other un-escaped sequences — none remain.
- **Verification**: The blocker was regenerated by invoking `registerCommandCodeNativeBlocker(false)` directly, and the regenerated output passes `node --check` and all behavioral tests (see §1).
- **Compliance Status**: **PASS** (Generated script syntactically valid and behaviorally correct).

### 3. RTK Rule Deployment Fallback Resolution (fixed in beta.8)
- **Finding**: `deployCommandCodeRtkRule` and `deployClaudeCodeRtkRule` resolved a nonexistent template path (`~/.konoha/.claude/rules/rtk.md`), producing `rtkRule: "rtk-rule-template-missing"` and leaving clients without the mandatory RTK output-filtering rule.
- **Fix**: A `resolveRtkRuleTemplate()` helper now resolves the first existing candidate: the bundled template (`~/.konoha/.claude/rules/rtk.md`) falling back to the authoritative RTK-managed global rule at `~/.claude/rules/rtk.md` (generated by RTK's own `rtk init -g`). `deployClaudeCodeRtkRule` additionally guards against same-file copies (src === dest returns `{ok: true}`).
- **Verification**: `ensureCommandCodeSetup` now reports `rtkRule: "deployed"`; the deployed `~/.commandcode/rules/rtk.md` is byte-identical to the authoritative `~/.claude/rules/rtk.md`.
- **Compliance Status**: **PASS** (Rule deploys reliably from the authoritative source).

### 4. Codex Client Deployment Hardening (fixed in beta.8)
- **Finding**: `deployCodexRtkRule` in `src/codex_manager.js` (a) failed on the same missing template path and (b) invoked `rtk init -g --codex`, an invalid command — RTK 0.44.1 supports `--agent` values `claude, cursor, windsurf, cline, kilocode, antigravity, kimi, pi, hermes, droid` and has no `codex` agent.
- **Fix**: The invalid spawn was removed entirely; the rule now deploys via direct copy with a `let src` fallback to `path.join(HOME, '.claude', 'rules', 'rtk.md')` when the bundled template is missing. `node --check` passes on the modified module.
- **Compliance Status**: **PASS** (No invalid external tool invocations; deployment path deterministic).

### 5. Runtime File Synchronization Invariant

- **Verification**: `diff` verified **ALL_IN_SYNC** for all three files after the beta.8 fixes.
- **Compliance Status**: **PASS** (Zero copy drift).
